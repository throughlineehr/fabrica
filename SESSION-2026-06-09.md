## What We Did This Session

### 1. Architectural Reframe

**Processors are infrastructure, agents are participants.**

- Processors: Wired into topology, always on, transform signals, run server-side
- Participants (users, agents): Enter rooms, subscribe to what interests them, come and go

This drives the architecture: signals run on server, frontend is view + command only.

### 2. Repo Restructure

```
fabrica/
  cmd/
    cli/            -- fabrica CLI (client-side, was daemon/)
    mcp/            -- MCP server for Claude Code (client-side, was mcp-server/)
  server/           -- THE Fabrica server (Go) - Step 1 complete
  web/              -- React frontend (was src/)
  connectors/       -- Slack etc.
```

**Key distinction:**
- `cmd/cli` and `cmd/mcp` are CLIENT-SIDE binaries downloaded by users
- `server/` is THE backend hosted by the organization
- They are NOT the same thing

### 3. User Model Defined

- Users added via OAuth invite
- Users assigned to rooms by cybernetician
- Being in a room = receive signals from that room
- Two roles: `user` and `cybernetician`
- Users have `scope_node_id` — can see that subtree
- Users can only ENTER rooms they're assigned to
- Cyberneticians can enter any room in their scope

### 4. UI for Users

One user entity, multiple views:
- Users tab (global list)
- Users panel in room (like Switchboard, shows users in this room)

Four ways to add user to room:
1. No room selected → "Add to Rooms" tool → hover → click
2. Room selected → add to selected
3. Inside room → Users panel → add at bottom
4. (Future) User page → add rooms

All send: `addUserToRoom(userId, roomKey)`

## Step 4 Complete

Signal processing on server — processors run server-side, signals flow to clients.

**Files added:**
- `server/signal.go` — Signal struct and helpers
- `server/bus.go` — Pub/sub message bus
- `server/dispatcher.go` — Cable routing
- `server/processor.go` — Processor interface and registry
- `server/processors_builtin.go` — Built-in processors (heartbeat, logger, tracer, test-generator)
- `server/runtime.go` — Processor lifecycle management

**How it works:**
1. Processor definitions registered at startup
2. When processor added, runtime.OnStateChange() starts it
3. Processors emit signals via dispatcher (for cables) and hub (for clients)
4. Clients receive signals as `{type: "signal", roomKey, signal}` messages

**Built-in processors:**
- `heartbeat` — Emits periodic metric signals
- `logger` — Logs received signals to console
- `tracer` — Passes signals through with trace info
- `test-generator` — Emits test event on start

## Step 5 Complete

Database persistence — state survives server restart.

**Files added:**
- `server/db.go` — PostgreSQL connection, migrations, state loading/saving, async StateSaver
- `server/migrations/001_schema.sql` — Schema for orgs, users, agents, assignments, vsm_state

**How it works:**
1. Server accepts `-database` flag with PostgreSQL URL
2. On startup: runs migrations, loads state from `vsm_state` table
3. On state change: `StateSaver.MarkDirty()` queues async save (1s debounce)
4. On shutdown: final save before exit

**Schema tables:**
- `organizations` — multi-tenant support (default org for now)
- `users` — email, role, scope_node_id, preferences
- `user_room_assignments` — user_id × room_key
- `agents` — AI agents with config
- `agent_room_assignments` — agent_id × room_key
- `vsm_state` — model, processors, cables as JSONB
- `invites` — OAuth invite tokens (future)

## Step 8 Complete

**Files changed:**

- `server/websocket.go` — Added ctx field to Client, filtered state broadcasts
- `server/commands.go` — Added login/logout/whoami commands, permission checks on room commands

**Auth commands:**
- `login(email)` → user (sets client context, sends filtered state)
- `loginAsAgent(agentId)` → agent (sets client context for agent)
- `logout()` (clears context)
- `whoami()` → { authenticated, role, rooms, scopeNodeId, userId/agentId }

**Permission rules enforced:**
- Users see only nodes in their scope (scopeNodeId subtree)
- Users can only modify rooms they're assigned to
- Cyberneticians can enter any room in their scope
- Unauthenticated clients get full state (backwards compat, can restrict later)

## Important Decisions

1. **Server in Go** — will become heavy streams processing, needs performance
2. **Signals run server-side only** — frontend never processes signals
3. **State shape matches frontend** — `{ model, processors, cables }`
4. **Permissions are scope-based** — users see subtree, enter assigned rooms only
5. **No Postgres blob** — that was a bad idea I proposed, user caught it
6. **60fps on frontend** — no processing there, just rendering
